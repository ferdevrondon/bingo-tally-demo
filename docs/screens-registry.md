**Status vocabulary used here:** `Done` (works end-to-end for its purpose) · `Partial` (real UI + real interactions, but key data/flow missing, **or** code complete but its phase acceptance test is not yet recorded) · `Stub` (renders, but content is hardcoded/template and buttons do nothing) · `Broken` (type-errors, or misused props / dead on arrival) · `Missing-but-linked` (nav points at a route that does not exist) · `Not started` (used only in the Planned section: specified in `BACKEND_PLAN.md`, no code yet).

**Persistence note:** Supabase is the source of truth for **auth**, the **single admin session** (Phase 2), the **catalog** (`players`, `round_templates`, Phase 3) and, since Phase 4b, the **live game session**.
- **Catalog.** `/players` and `/rounds` read through `lib/data/players.ts` / `lib/data/rounds.ts` and write through Server Actions, the same as before.
- **Reads for the live game.** `lib/round-draft/fetch-state.ts` (`fetchGameSessionState`) reads the house's `status = 'active'` game session: catalog players, `game_session_players`, `tickets`, `ticket_numbers`, `game_session_rounds` and the last `activity_log` rows. It builds a `RoundDraftState` from them. The same function runs on the server (`lib/data/load-game-session.ts`, `cache()`d, used by the `(game)` layout) and in the browser (the provider's background re-sync).
- **Writes for the live game.** They go **straight from the browser** to the 4a SQL functions via `supabase.rpc` (`lib/round-draft/game-api.ts`), each with a fresh `request_id`. `lib/round-draft/context.tsx` applies frequent actions optimistically, runs the calls through an ordered promise queue, then re-reads the game session about 100 ms after the queue goes idle (300 ms before Phase 5). The browser re-sync passes the known game session id, so its rows are read together with the active game session in one round trip.
  - **Phase 5:** it also re-reads on every Realtime `activity_log` row of the house, and on a channel reconnect. The same yields apply: none while this tab has actions in flight, and none once this tab is ending or discarding the game session. For observers, `perform` returns `read_only` without dispatching or calling SQL.
  - Structural actions await that read, and they are not optimistic: add ticket, pick round, close round.
  - End and discard skip the re-read.
  - Errors show a Spanish sonner toast (`GAME_ACTION_ERROR_MESSAGES` in `lib/data/game-action-result.ts`), and the re-sync reverts the optimistic change.
  - The only Server Action is "Iniciar jornada" (`lib/data/game-session-actions.ts` → `startGameSession`), because it redirects.
- **Gone:** `storage.ts` (localStorage), `lib/round-draft/players.ts` (`SYNC_CATALOG`), `LOG_ACTIVITY`, the seed activity, `NUMBER_PRICE` and `hasDraftProgress`. The reducer charges and refunds at the open round's `linePrice`.
- **Game rules v2 (4c):**
  - **Balance.** A player has one signed `balance` per game session (`game_session_players.balance`), not the positive/negative pair. `lib/round-draft/balance.ts` shows it as "Debe $X" / "A favor $X" / "Al día", or as `±$X`.
  - **Prizes.** A round template has no kind: it has 1–5 prizes. The round copies them when it starts. Each winning ticket is paid `prizes[slot]`; a gifted ticket is paid prize − P (`prize-rules.ts` `ticketPrize`).
  - **Check-in** moves no money.
  - **House result.** `game_sessions.house_balance` is the house result: sales − prizes + the round margin (gifts that lost, unsold numbers that lost, unsold numbers that won). Recharges are cash and do not count.
  - **Summaries.** Closing a round reads `fetchRoundSummary()`. Ending the game session reads `fetchSummary()`. Both come from `game-api.ts` and are shown with `components/house-result-breakdown.tsx`.
- **Player accounts and settlements (4d1 + 4d2):**
  - **Account.** `player_accounts.balance` is one signed balance per player that carries over between game sessions, plus `balance_status` (`play` | `pending_payout` | `owes`) and `balance_note`. A player joining a game session opens with it (`game_session_players.opening_balance`), and it goes back to the account when the game session ends. `lib/accounts.ts` labels it "Debe" / "Al día" / "Para jugar" / "Pendiente de pago" / "Por definir"; `lib/data/accounts.ts` reads it.
  - **Live game.** `fetchGameSessionState` now also reads `player_accounts`, so a catalog player who has not joined shows their account balance (S-05 player list, S-06).
  - **Account writes (`/players`, M-21's data).** Server Actions in `lib/data/account-actions.ts`: `receivePayment` → `record_account_recharge`, `registerPayout` → `record_account_payout`, `setBalanceStatus` → `set_balance_status`, `getStartAlerts` (read). A move for a player who is in the active game session goes to that game session.
  - **Settlement.** `end_game_session` opens one `settlements` row plus one `settlement_players` row per player. Reads: `lib/data/settlement.ts` (`loadSettlement`, `listSettlements`; the per-player breakdown reads the game session's `activity_log` page by page). Writes: `lib/data/settlement-actions.ts` → `settlement_receive`, `settlement_payout`, `settlement_mark`, `close_settlement`. A closed settlement rejects changes (`settlement_closed`).
  - **Errors.** Every one of these Server Actions reports through `lib/data/reject-game-action.ts` (moved out of `game-session-actions.ts`, now shared with "Iniciar jornada"): 42501 → `rejectWrite()` (replaced session → M-13, else "Solo lectura"), other codes → `GAME_ACTION_ERROR_MESSAGES` (eight new Spanish messages). The client shows a toast; there is no inline error except M-20's required note.
- **Game session reports (Phase 6a):** `lib/game-report/` reads with any Supabase client (like `fetch-state.ts`). Server: `lib/data/game-sessions.ts` → `listGameSessions()` (S-07, S-10 Jornadas tab, S-03), `loadGameSessionReport(id)` (S-17; `null` for an unknown id or another house's, via RLS + `maybeSingle`) and `loadHomeSummary()` (S-03). Browser: `fetchClosedRounds()` (S-06 `LiveRoundHistory`, re-read whenever `state.roundsPlayed` changes) and `fetchPlayerRounds()` (M-06 / M-11, read when the dialog opens). Dates use the house time zone (`lib/game-report/format.ts`); the S-06 heading and the S-17 timeline format them on the client only. `fetchGameSessionState` now also carries `gameNumber` and `gameStartedAt`.
- **Reportes as routes (Phase 6b1):** `lib/data/game-sessions.ts` → `loadRoundsOfDay(day)` (S-21; an invalid or missing `?date=` falls back to today in the house time zone, `houseToday` / `isDayString`) → `fetchRoundsOfDay()` in `lib/game-report/fetch.ts`: the game sessions whose `started_at` falls in that house day (`houseDayRange`, DST-safe), each read with `fetchGameSessionReport`, keeping played rounds only; the day total is the sum of the rounds' house results. `lib/data/debts.ts` → `listDebts()` (S-22, `cache()`d): active players, `listPlayerAccounts()` (live balance while in a game session), method, bank, and each player's last game session (from `game_session_players`, paged by 1000); only non-zero balances.

- **Live refresh (Phase 5):** the server-rendered pages S-03, S-08, S-20, S-18 and M-18 mount `LiveRefresh`, which calls `router.refresh()` 250 ms after any new `activity_log` row of the house. Client state (an open dialog, a typed amount) survives the refresh. **Phase 6a:** also mounted on the report pages; **since 6b1** they are S-10 `/reports/games`, S-17 `/reports/games/[id]`, S-21 `/reports/rounds` and S-22 `/reports/debts`.
